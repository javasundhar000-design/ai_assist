# Fixing "Android Gradle plugin supports only Kotlin Gradle plugin
version 1.5.20 and higher" (ar_flutter_plugin)

## The problem

`ar_flutter_plugin ^0.7.3`'s own Android module
(`android/build.gradle` inside the package) declares a hardcoded,
ancient `kotlin-gradle-plugin:1.3.50` dependency in its own
`buildscript` block. Modern Android Gradle Plugin (AGP) versions
refuse to build at all if *any* included module's buildscript
classpath resolves to a Kotlin Gradle Plugin below 1.5.20 — so this
fails the whole build, not just that one plugin's compilation.

This is a real, known limitation of `ar_flutter_plugin` being an old,
infrequently-updated package — not something specific to your
machine or Flutter 3.16.7.

## Fix: force the Kotlin Gradle Plugin version at the buildscript level

Open **`android/build.gradle`** (top-level, generated by
`flutter create` — not `android/app/build.gradle`). It should already
have a `buildscript { ... }` block near the top, something like:

```groovy
buildscript {
    ext.kotlin_version = '1.7.10'   // whatever version is already there
    repositories {
        google()
        mavenCentral()
    }
    dependencies {
        classpath 'com.android.tools.build:gradle:7.3.0'  // keep as-is
        classpath "org.jetbrains.kotlin:kotlin-gradle-plugin:$kotlin_version"
    }
}
```

Add a `configurations.classpath { resolutionStrategy { force ... } }`
block **inside** that same `buildscript { }` block (order doesn't
matter, just keep it inside the braces):

```groovy
buildscript {
    ext.kotlin_version = '1.7.10'
    repositories {
        google()
        mavenCentral()
    }
    dependencies {
        classpath 'com.android.tools.build:gradle:7.3.0'
        classpath "org.jetbrains.kotlin:kotlin-gradle-plugin:$kotlin_version"
    }

    // --- ADD THIS ---
    // ar_flutter_plugin's own android/build.gradle hardcodes an ancient
    // kotlin-gradle-plugin version (1.3.50) that current AGP rejects.
    // Force every module's buildscript classpath resolution — including
    // ar_flutter_plugin's — onto the version declared above instead.
    configurations.classpath {
        resolutionStrategy {
            force "org.jetbrains.kotlin:kotlin-gradle-plugin:$kotlin_version"
        }
    }
}
```

Make sure `ext.kotlin_version` is at least `1.7.10` (bump it if it's
lower — anything from 1.7.10 through the 1.9.x line should satisfy
AGP's 1.5.20+ requirement comfortably).

Then re-run:

```
flutter clean
flutter pub get
flutter run
```

## Why `allprojects { configurations.all { ... force ... } }` alone
## won't fix this

That's the more commonly-copy-pasted Gradle snippet for version
conflicts, but it only affects each subproject's own *dependency*
configurations (`implementation`, `api`, etc.) — not the buildscript
classpath used to *load and apply Gradle plugins themselves*, which
resolves in an earlier, separate phase. The fix has to target
`buildscript.configurations.classpath` specifically, at the root
project level, as above.

## If forcing the version doesn't fully resolve it

Some very old plugins have deeper incompatibilities beyond just the
Kotlin version (removed Gradle APIs, deprecated AGP hooks, etc.). If
you hit a *different* Gradle error after this fix, paste it back and
I'll address that one specifically.

If `ar_flutter_plugin` turns out to have compounding issues, the
fallback — flagged as a real possibility back in the Phase 12 notes —
is migrating to platform-specific `arcore_flutter_plugin` (Android) +
`arkit_plugin` (iOS) behind the same `ArSessionService` interface
already built in this project (`lib/features/ar_visualization/services/
ar_session_service.dart`). That interface exists specifically so this
kind of plugin swap is a contained rewrite of one file's internals, not
a redesign of the AR feature. Say if you want to go that route and I'll
do the migration.
